# 규모와 증거 강도

절차의 무게를 작업의 무게에 맞춘다. 이 문서가 없으면 4줄짜리 문서 수정과
40파일 리팩터가 같은 의례를 받는다 — 실제로 그렇게 굴러왔다.

## 두 축은 서로 다른 것을 정한다

```text
증거 강도 (L0/L1/L2)   변경 규모와 성격이 정한다   →  무엇을 증거로 남길 것인가
저장소 프로파일 (solo/team)   저장소 성격이 정한다   →  얼마나 많이 전달할 것인가
```

**프로파일이 증거 종류를 정하지 않는다.** 팀 저장소라고 3줄 수정에 스크린샷이
더 유용해지지는 않는다. 반대로 1인 저장소라도 화면 배치를 12파일 고쳤으면 눈으로 봐야 한다.

이 둘을 한 축으로 묶으면 "팀이니까 전부 무겁게"가 되어 원래 문제로 돌아간다.

## 증거 강도

```text
L0  명령 출력   종료 코드와 출력 원문만 남긴다. 전후 캡처 단계를 아예 돌지 않는다
L1  실측       바뀐 값을 직접 재서 전후로 비교한다. 캡처는 만들지 않는다
L2  시각       webp 전후 + 바운딩 박스. 배치 자체가 산출물일 때만
```

### 판정 규칙

```text
완료 기준에 추론된 동작이 있다        →  최소 L1
화면 변경이고 4파일 초과 또는 30줄 초과  →  L2
화면 변경이지만 그보다 좁다            →  L1 (바뀐 속성만 잰다)
그 외                                →  L0
```

`.issue/**` 는 규모 계산에서 뺀다. 증거를 변경분으로 세면 증거가 규모를 키우고
커진 규모가 다시 더 많은 증거를 요구한다. 캡처 두 장 때문에 3파일이 12파일로 잡힌다.

### L1 의 방아쇠 — 가장 자주 빠뜨리는 축

`--inferred` 는 **완료 기준에 구현자의 "이렇게 동작할 것이다"가 들어 있을 때** 붙인다.
규모가 작아도 추론이 근거로 쓰이면 그 추론은 재야 한다.

추론이 자주 틀리는 영역:

- CSS 오류 복구 — 잘못된 셀렉터가 어디까지 삼키는지
- 캐시 무효화 — 무엇이 언제 비워지는지
- 동시성·경합 — 순서가 실제로 어떻게 잡히는지
- 정규식 매칭 범위 — 코드펜스 안까지 훑는지 아닌지

실제 사례: `page-switch.css.template` 의 `#` 주석 한 줄이 CSS 파서에서
`.nav-segment` 규칙 **전체**를 삼켰다. 추론으로는 "주석이 무시되겠지" 였고,
`getComputedStyle` 로 재 보니 5개 속성 중 0개가 적용돼 있었다.
2파일 15줄짜리 변경이었지만 이 측정 하나가 이슈 전체의 근거였다.

반대로 같은 이슈에서 만든 webp 전후 캡처 두 장은 같은 사실을 예쁘게 반복한 것이었다.
숫자로 증명되는 것을 그림으로 한 번 더 보여주는 것은 반복이지 증거가 아니다.

## 저장소 프로파일

```text
solo   리뷰어 신호가 없다. 활동 기여자 1명, CI·템플릿 없음, 비공개
team   그 중 하나라도 있다
```

활동 기여자는 **커밋 2개 이상인 저자**만 센다. 초기 임포트나 스캐폴딩 커밋 하나로
1인 저장소가 team 으로 넘어가는 오판이 실제로 난다.

애매하면 team 으로 기운다. 과하게 남긴 증거는 낭비지만,
남이 읽어야 할 때 없는 증거는 되돌릴 수 없다.

프로파일이 정하는 것:

```text
승인 게이트   solo 는 마지막에 한 번. team 은 push 와 PR 을 나눠 받는다
산문         어느 쪽이든 comment.md 가 결과 정본이다. PR 본문은 그것을 링크한다
```

## private 저장소

raw 이미지 URL 은 비공개 저장소의 이슈 코멘트에서 렌더링되지 않는다.
그래서 `MIRROR_EVIDENCE=0` 이 되고 기본 브랜치 미러 단계가 사라진다.
이건 규칙 위반이 아니라 해당 없음이다 — 미러의 목적이 이미지 렌더링이기 때문이다.

증거 자체는 작업 브랜치에 커밋돼 있고 PR 이 merge 되면 기본 브랜치로 함께 들어간다.
코멘트에는 이미지 대신 수치와 명령 출력을 표로 싣는다.

**매번 사용자에게 예외 승인을 받지 않는다.** 판정은 `route` 가 이미 했다.

## 계산

```bash
node <skill>/scripts/issue-start.mjs route {issue} --kind <성격> [--inferred] [--files N --lines N]
node <skill>/scripts/issue-create.mjs profile          # 프로파일만
```

### 규모는 구현 전에 추정해서 넘긴다

`route` 는 3단계에서 불린다. 그 시점의 diff 는 비어 있으므로 잰 값만 믿으면
규모가 늘 0 이 되고, 화면 변경도 전부 "좁은 범위"로 분류되어 **L2 가 도달 불가**가 된다.

`plan.md` 의 영향 범위에서 파일 수와 줄 수를 뽑아 `--files` / `--lines` 로 넘긴다.
`CHANGE_SCALE_WARN=` 이 나오면 빠뜨린 것이다.

구현 뒤 9단계에서 인자 없이 다시 부르면 실측값이 잡힌다.
추정과 실측이 크게 어긋났으면 보고하고 증거 강도를 조정한다 —
"4파일로 예상했는데 11파일을 고쳤다"는 그 자체로 계획이 틀렸다는 신호다.

프로파일은 한 번 정해 `.issue/settings.json` 에 남고 네 스킬이 같은 값을 읽는다.
저장소 성격은 자주 바뀌지 않고, 실행마다 값이 흔들리면 증거 기준도 흔들린다.
다시 정하려면 `profile --profile <solo|team>`.

## 뺀 단계는 반드시 보고한다

`SKIPPED=` 를 사유와 함께 사용자에게 알린다. 조용히 건너뛰면 "다 했다"로 읽혀서
안 한 것보다 나쁘다. 줄인 것이 보여야 줄인 것이다.

```text
건너뜀   10. 증거 미러 — private 저장소라 raw 이미지가 코멘트에서 렌더링되지 않는다
        12. 메인 최신화 — 기본 브랜치에 올린 것이 없다
```
